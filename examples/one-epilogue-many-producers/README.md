# One epilogue, many producers

One unchanged hand-CUDA epilogue imports a 128×128 f32 accumulator tile and a
row-scale vector from two independently packaged providers, then computes
`out[m,n] = max(acc[m,n] * scale[m] + bias[m], 0)`. It links against TMEM, smem
and TileLang-register providers on Blackwell/sm103, WGMMA-register, smem and
TileLang-register providers on Hopper/sm90, and `mma.sync`-register, smem and
TileLang-register providers on consumer Blackwell/sm120. Each profile has three hand-consumer
cells plus three `-tlc` contract-authored TileLang-consumer cells: a **6 + 6 + 6**
matrix. The hand consumer is 78 lines with 11 direct annotations; no placement-
specific source edits are needed.

SASS is diagnostic, not a replacement for the scored same-source control.

The CUDA providers run a pipelined GEMM core: a three-slot ring of K64 operand
tiles filled by TMA and consumed by tcgen05 (sm103, `gemm_mainloop_sm100.cuh`),
one-warpgroup WGMMA (sm90, `gemm_mainloop_sm90.cuh`) or four-warp `mma.sync` fed by
`ldmatrix` (sm120, `gemm_mainloop_sm120.cuh`). Their A/B tensor maps
are the roleless provider's own `PL_PARAMS`, reached through the linker-generated
`pipelink_params_<stage>()` accessor; `params.py` encodes them with
`tools/tensormap.py`. Shared-memory exports reuse the dead operand ring and
declare an XOR-swizzled placement. The TileLang provider uses 16-byte cp.async
(TMA lowering and automatic warp specialization stay disabled against a foreign
partner; on sm103 it lowers to `mma.sync`). The row-scale provider and the
natives share `providers/rowscale/row_scale.cuh`, a warp-cooperative 16-byte
reduction.

Register and TMEM accumulator providers declare their operand arena live only
from `tensor_work` to `tensor_ready`; it is not backing for the exported value.
The CUDA mainloops drain asynchronous accesses and join all provider threads
before one thread invalidates every ring mbarrier (including the accumulator
barrier on sm103). This follows the [PTX mbarrier invalidation rules](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-mbarrier-inval):
the barrier must no longer be in use before its storage is repurposed. Natives
call these same mainloops and pay the same synchronization cost. Smem exports
keep the ring kernel-lived because it holds their exported tile. The TileLang
register backend derives the same lifetime for its barrier-free operand arena.
Both teaching consumers promise `single_completion`: each import's completion
helper is called exactly once, after its final use. These declarations let the
linker reuse the dead operand arena for import scratch (see the
evidence below).

`native/` holds hand-fused single-stage controls, one per mainloop:
`fused_sm100.cu`, `fused_sm90.cu`, `fused_sm120.cu`, and a TileLang-mainloop native generated by
`native/generate_tilelang.py` from the lowered provider. Each uses the same
mainloop source, row-scale body and epilogue arithmetic, but reads the
accumulator where the MMA left it: no import adapter, import scratch or caller
frame. Linked-vs-native is a characterization, **not** the same-source one-TU
parity ratio and not a gate.

The teaching tree owns its accumulator sources under `providers/accumulator/`
and their small include closure under `providers/abi/`. It does not import the
tensor-import research build: research keeps independent copies for replay,
while both use the shared environment and packaging helpers in `tools/`.

## Commands

From the repository root, configure CUDA 13.3 and scratch via `.env`
([T0](../../docs/tutorials/T0-pack-link.md)). Obtain the patched TileLang 0.1.14
wheel with [`frontends/tilelang/env/build-tilelang.sh`](../../frontends/tilelang/env/build-tilelang.sh)
if absent, following the [frontend environment instructions](../../frontends/tilelang/env/README.md).
The full recipe needs the repository CUTLASS headers and pinned TileLang backend,
including for non-alias adapters of hand-written consumers. Builds are GPU-free;
all generated packages, controls and evidence are locally ignored under `out/`.
Until the GitHub release asset exists, the lock pins the owner's local wheel
hash; refresh its TileLang entry after a source rebuild before the locked sync.

```sh
source tools/env.sh
uv lock --project frontends/tilelang --refresh-package tilelang
uv sync --project frontends/tilelang --locked
mkdir -p "$PIPELINK_SCRATCH_ROOT/one-epilogue"
export TMPDIR="$PIPELINK_SCRATCH_ROOT/one-epilogue"
export PIPELINK_TILELANG_PYTHON="$PWD/frontends/tilelang/.venv/bin/python"
export TILELANG_INCLUDE_DIR="$PWD/frontends/tilelang/.venv/lib/python3.11/site-packages/tilelang/src"
export CUTLASS_INCLUDE_DIR="$PWD/third_party/cutlass/include"
export EX=examples/one-epilogue-many-producers

for P in sm_103a sm_90a sm_120a; do
  O="$PWD/$EX/out/$P"
  uv run --project pipec --locked python "$EX/build.py" --profile "$P"
  "$PIPELINK_TILELANG_PYTHON" -m pipelink_tilelang \
    --kernel "$EX/providers/tilelang/gemm_provider.py" --profile "$P" --out "$O/tilelang/provider"
  uv run --project pipec --locked pipec2 pack "$O/tilelang/provider/roles.cu" \
    -o "$O/packed/tl-reg.plink" -I "$CUTLASS_INCLUDE_DIR" -I "$TILELANG_INCLUDE_DIR" --profile "$P"
  PIPELINK_ACC_PARTNER="$O/packed/tl-reg.plink" PIPELINK_SCALE_PARTNER="$O/packed/rowscale.plink" \
    "$PIPELINK_TILELANG_PYTHON" -m pipelink_tilelang \
    --kernel "$EX/consumer-tilelang/epilogue_contract.py" --profile "$P" --out "$O/tilelang/consumer"
  uv run --project pipec --locked pipec2 pack \
    "$O/tilelang/consumer/generation/tilelang-epilogue/roles.cu" -o "$O/packed/tl-epilogue.plink" \
    -I "$CUTLASS_INCLUDE_DIR" -I "$TILELANG_INCLUDE_DIR" --profile "$P"
  uv run --project pipec --locked python "$EX/pipelines/extra_cells.py" "$P"
  uv run --project pipec --locked python "$EX/build.py" \
    --profile "$P" --extra-cells "$O/extra-cells.json"
done
```

Run only on a GPU matching the selected profile. `--gpu` is physical; the runner
selects it before initializing CUDA. Without `--gpu`, it uses
the first `.env` `PIPELINK_GPUS` entry. Each run writes fresh
`out/<profile>/results.json`. It verifies every cell and native against the f64
oracle at 256×256×K (K = 64, 256, 1024); times linked vs one-TU (same buffers)
and linked vs its native (own buffers, identical inputs) at 4096×8192×4096;
and runs memcheck, racecheck and synccheck on linked, one-TU and native
images at 128×128×64 and 256×256×512 (the latter wraps the operand ring more
than twice).

```sh
# On Blackwell/sm103, using an available physical GPU:
uv run --project pipec --locked python examples/one-epilogue-many-producers/run.py --profile sm_103a
# On a Hopper/sm90 machine with the matching built outputs:
uv run --project pipec --locked python examples/one-epilogue-many-producers/run.py --profile sm_90a
# On a consumer Blackwell/sm120 machine with the matching built outputs:
uv run --project pipec --locked python examples/one-epilogue-many-producers/run.py --profile sm_120a
```

## Evidence

### Measured acceptance

CUDA 13.3; observed SM clocks 2032 MHz on Blackwell/sm103, 1920–1980 MHz on
Hopper/sm90 (H200) and 2930–2950 MHz on consumer Blackwell/sm120 (RTX 5090).
Clocks were neither changed nor locked: the ratios describe paired
alternations, not locked-clock throughput claims. Every profile: status PASS,
0 oracle mismatches in every cell and native, linked/one-TU bitwise equal
including the benchmark, 12/12 sanitizer runs per cell (memcheck, racecheck
and synccheck on linked and one-TU at both sanitizer shapes) and 6/6 per native.
Timing uses one benchmark shape, 4096×8192×4096.
One-TU/linked is the same-source one-TU parity ratio; linked/native > 1 means
the linked kernel is slower.

Every staged register cell overlaps its 64 KiB import scratch with the
provider's operand arena (`link.json` → `tensor.smem_reuse.overlaps`, witness
`pl_import_acc_ready`).

one-TU (same counts); the backend-matched LTO control is SASS-identical to linked.

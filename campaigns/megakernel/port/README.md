# Megakernel stage packages

Publication replaces machine-local paths in recorded evidence with placeholders;
measurements and verdicts are unchanged.

## Host ABI-v3 packages

Each composition contains the interpreter and eight op packages. Pipeline `a`
uses ThunderKittens throughout; pipeline `cute` swaps in a CUTLASS/CuTe
partial-attention package and reuses the other eight packages and the host provider.
`build.sh` packs the annotated `.cu` files directly with `pipec2 pack`, which derives
each stage manifest and resource envelope from the annotations and compiler-measured
layouts. `src/mk_abi.cuh` registers each op's six exports, matching call endpoints,
instruction-phase claims and advisory hints. Each pipeline has its own same-source
one-TU control; the monolithic control uses the upstream ThunderKittens bodies.

`sizeof`, `alignof`, configuration constants, and upstream pipeline constants
supply resource sizes. The interpreter is the sole host owner
`org.pipelink.megakernel`, with group `org.pipelink.megakernel.params`. It and
the export-only ops use `PL_NO_PARAMS()`. `PL_HOST_GROUP` automatically reflects
the installed neutral C ABI inventory in the interpreter's emit translation unit.
The owner's `PL_HOST_ABI_TYPE` declarations reflect `MkProviderArgs` and the five
role views; `PL_HOST_ABI_EMPTY` measures the opaque `mk_globals` residue
(9600 bytes, alignment 128). ThunderKittens `gl`
has a user-provided copy constructor, so the provider constructs it and copies
its representation into the residue rather than exposing a member-layout claim.
Every interpreter role receives a generated view and reads `view.residue`.

The four exports are `pipelink_params_{abi,query,build,release}_interpreter`.
`abi` is generated by `pipec2.host.provider.build_provider` from the packed
manifest's owner-contract digest and dtype digest. The provider build independently
probes the neutral and owner-local layouts and requires its complete compiler
inventory to equal the packed inventory; only owner-local type IDs are supplied.
`query` is the geometry authority: one CTA per SM, with block, cluster and dynamic
shared memory from the link's static constraints. Device resources and `pos_id`
remain owner-typed args, not channels.

The four files in `pipelines/` are integration templates: wiring, opcode capacity,
phases, and opcode permutations. The link step fills target, physical capacities,
storage placement, and register choices from the packed interpreter; it writes
complete linker inputs to `build/pipelines/`. These templates are not standalone
`pipec2 link` inputs.

### Cross-library attention

[`cute_attention.cuh`](src/ops/cute_attention.cuh) implements QK, online softmax
and PV with CuTe layouts, asynchronous vector copies, `ldmatrix` and BF16
warp-level MMA. Four independent consumer warps process 32-token KV tiles,
using FP32 softmax state and BF16 probabilities. Their normalized outputs and
base-2 LSEs are merged before the existing external attention reduction. The math
core includes only CuTe and CUTLASS headers.
[`attn_partial_cute.cu`](src/ops/attn_partial_cute.cu) adapts it to the VM's
page, semaphore, instruction and global-completion protocols and claims four
pages and four semaphores.

The stage is built directly from CuTe primitives. The instruction stream, KV partition
count, remaining stages and host buffers are identical to the all-ThunderKittens
reference. The stage uses warp MMA; a `tcgen05` version with a transposed small-query
mapping is possible but has not been implemented or measured.

After building the reference packages and host binaries:

```sh
CASE=campaigns/megakernel
bash "$CASE/port/build.sh" --cute
uv run --project pipec --locked python "$CASE/host/launch.py" \
  --pipeline cute --image linked --gpu "$MK_GPU" \
  --bundle "$CASE/host/bundles/p1024-n8-red" \
  --out "$PIPELINK_SCRATCH_ROOT/cute-attention-check"
```

`--cute` packs only `op_attn_partial_cute.plink`, derives `build/pipelines/cute.json`
from `a`, links it with the eight existing packages, and builds
`build/onetu/cute.cubin`. Use `--image onetu` for its same-source control and
`--pipeline a --image linked` for the all-ThunderKittens reference. The normal build
includes both implementations. A replacement-only build records itself in
`build-record-cute.json` and leaves the reference's `build-record.json` and published
receipts untouched.

An independent double-precision oracle covers sequence tails, partition sizes that
do not divide the sequence, and empty splits:

```sh
mkdir -p "$PIPELINK_SCRATCH_ROOT/cute-attention"
"$PIPELINK_CUDA_HOME/bin/nvcc" -O3 --use_fast_math -std=c++20 -arch=sm_103a \
  -Ithird_party/cutlass/include "$CASE/host/check_cute_attention.cu" \
  -o "$PIPELINK_SCRATCH_ROOT/cute-attention/check"
CUDA_VISIBLE_DEVICES="$MK_GPU" "$PIPELINK_SCRATCH_ROOT/cute-attention/check"
```

`host/compare.py` checks the CuTe pipeline with the same predicates as the reference
campaign. Gated runs are PipeLink images (linked, its repeat, one-TU); the two
monolithic ThunderKittens runs are the baseline that sets the repeat floor and the
upstream-equivalence target. Layer-1 `hidden_states` and `silu_out` are reported
against the PyVM reference and gated through upstream equivalence, so a different
but equally accurate attention arithmetic passes.

#### Measured composition

The [CuTe composition evidence](../evidence/CUTE-RESULT.md) runs the reference
campaign's definitive P3 protocol on the same seeded random-weight Llama-3.2-1B
bundles. At 1102 MHz on Blackwell/sm103, eight valid pairs per case give:

| Context / KV partitions per head | ThunderKittens ms/token | CuTe composition ms/token | Paired speedup | Linked / same-source throughput |
|---|---:|---:|---:|---:|
| 16 / 1 | 0.7939 | 0.7973 | 0.996× | 0.9999 |
| 1024 / 2, with reduction | 1.1980 | 0.9834 | 1.218× | 1.0000 |
| 4096 / 1 | 3.7330 | 1.7010 | 2.195× | 0.9999 |

The speedup is the median paired throughput ratio of the CuTe and all-ThunderKittens
linked kernels; the last column is the CuTe composition's own seam-parity ratio
against its one-TU build, and every case clears the 0.97 seam-parity floor. All
25 P2 numerical receipts (ThunderKittens and CuTe) pass, and the timed images have
zero memcheck and synccheck findings. The linked and one-TU images have identical
normalized SASS (REG96/STACK880/SHARED2048/LOCAL0, no ptxas register spills).

To reproduce, run the CuTe sanitizer pass and then P3 after `build.sh --cute`:

```sh
export MK_GPU="${MK_GPU:?Set MK_GPU to an available positive physical GPU index}"
uv run --project campaigns/megakernel/host --locked python \
  campaigns/megakernel/evidence/parity/run_parity.py --suite cute --sanitize
uv run --project campaigns/megakernel/host --locked python \
  campaigns/megakernel/evidence/parity/run_parity.py --suite cute
```

The attention oracle passes all 70 tail/partition cases with zero memcheck,
synccheck and racecheck findings. All five P2 numerical receipts pass: three at full
depth, and both layer-1 fixtures with the strict Q/attention/K/V checks, the
zero-logit and untouched-cache checks, linked/one-TU agreement and upstream
equivalence. Layer-1 `silu_out` misses the strict PyVM tolerance on 36–40 of 65,536
elements, as the ThunderKittens control does on 35–53.

**The full composition is not racecheck-clean.** For the short and reduction
fixtures, linked and one-TU images have zero memcheck and synccheck findings, while
racecheck reports 25/26 and 33/33 hazards respectively. The capped reports cover
ThunderKittens matvec scratch and the VM instruction ring; the CuTe adapter appears
only as a reader of that ring. No reported PC maps to the CuTe math core, although
capped logs cannot rule it out. The all-ThunderKittens reference has its own
racecheck findings, recorded with its evidence.

### Build and evidence

From the repository root:

```sh
export MK_GPU="${MK_GPU:?Set MK_GPU to an available positive physical GPU index}"
bash campaigns/megakernel/port/build.sh --through link
bash campaigns/megakernel/port/build.sh --from onetu
bash campaigns/megakernel/host/run.sh
bash campaigns/megakernel/evidence/run.sh
```

The first command is host-only and also builds `host/build/provider.so`,
`provider_selftest`, and `mk_runner`. To rebuild just those binaries after an
interpreter pack, run `bash campaigns/megakernel/host/build_provider.sh` and
`bash campaigns/megakernel/host/build_runner.sh`. The provider build does not run
the GPU selftest; `host/run.sh` does so explicitly on `MK_GPU`.
The second command rebuilds all same-source controls and the upstream monolithic
control, then records P1 resource/seam evidence. The last two commands run the
hardware correctness/sanitizer and clock-locked performance workflows respectively;
choose available GPUs via `MK_GPU` (and optionally `MK_REF_GPU` for reference export).
Parity slots use `PIPELINK_SCRATCH_ROOT` from the repository environment configuration.

Each `build.sh` invocation writes a fresh `build/build-record.json` generation,
the linked/one-TU image paths, and non-gating `nvcc --version` provenance.
P2 sanitizer receipts carry that generation and identify coverage by case,
image role, path, and tool. P3 requires the current generation and all covered
linked/one-TU images; after rebuilding, rerun P2 sanitizers before P3.
No rebuilt cubin is compared with a recorded content hash. The shared parity
harness still computes image and stream-map digests from the current files
at run time for its same-invocation boundary checks.
Acceptance requires memcheck success; racecheck and synccheck counts are
recorded, not required to be zero. Seam parity does not imply sanitizer-clean
acceptance.

The required additional pack flags are `-std=c++20`, `--expt-extended-lambda`,
`--expt-relaxed-constexpr`, `--use_fast_math`, and the per-stage
`--frandom-seed=<stage>`, passed through repeatable `--nvcc-flag`. The existing
`KITTENS_HOPPER=1` and `KITTENS_BLACKWELL=1` build definitions use `-D`.
The provider also requires C++20 because the unchanged ThunderKittens headers use
concepts. The native runner and public-header-only selftest compile as C++17.

`host/launch.py --print-only` derives the native runner's ABI flags from
`link.json.host`: `--params-bytes`, `--params-align`, `--residue-offset`,
`--residue-bytes`, `--owner-id`, `--dtypes-digest`, `--owner-contract`,
`--threads`, `--cluster X,Y,Z`, and `--dyn-smem`. The other required flags are
`--cubin`, `--kernel`, `--provider`, `--bundle`, `--out`, `--mode check|bench`,
and `--opcode-map`. Check mode accepts `--ntok` and `--pos-id-first`; bench mode
requires `--bench-seconds`, `--bench-discard`, `--bench-batch-tokens`, and
`--pos-id`, with optional `--sync-each 0|1`. Geometry is never caller-supplied.

The native client checks the ABI report once against the link identity and layout.
For each check token it sets `pos_id`, calls `query`, builds a fresh session into
the residue with transfer capacity zero, launches, synchronizes, and releases.
Every attempted build is released, including failures. Bench mode fixes `pos_id`
within a batch and reuses one immutable session for that batch only. The monolithic
control uses the same provider but receives just the raw residue as its params.

Artifacts are `build/artifacts/{interpreter,op_*}.plink`. Pack receipts and
inspections are in `build/logs/`; `build/linked/*/link.json` records the new input
hashes. This port has no separate frozen-artifact ledger or freeze command.
Repacking produces new artifacts, not new GPU evidence: recorded P1, P2 and P3
results describe the images they measured until their workflow is rerun, and pack
does not rewrite parity JSONs.

### Current gate results

All nine packages record fast math in `pipelink_abi.target.math`: FTZ and FMA
enabled, precise division and square root disabled. The linked, same-source
one-TU and monolithic images use that mode consistently and the current host ABI v3.

The provider selftest passes. All **20/20** P2 receipts pass across five bundles and
four pipelines. Every linked/one-TU floor/ULP and upstream-equivalence predicate
passes, and the required layer-0 K/V rows are bitwise repeatable. At full depth,
random-weight layers make repeats differ, so distances are judged against the
repeat floor: the larger of the linked and monolithic repeat differences. Distance
to the PyVM reference is gated on mean relative difference within twice that
floor; its per-element maximum is reported. The monolithic runs are the baseline
and are not gated themselves. The [evidence report](../evidence/RESULT.md)
records the sanitizer and seam-parity verdicts. Receipts are
`../host/runs/<bundle>/compare-<pipeline>.json`, with reduction-bundle receipts
under `../host/runs/submission-2026-09-17/`.

Gate P1 **PASS** for `a`, `rebind-smem`, `rebind-regs`, and `rebind-opcode`,
with zero seam symbols and histogram violations. All linked/one-TU pairs have
REG/STACK/SHARED/LOCAL = **96/896/2048/0**, two CALLs and 50 MUFUs each.
Their complete normalized SASS instruction sequences are identical under
`evaluator/gates/normalization.py`. The P1 records are `build/gate_p1.json`
and `build/logs/gate-p1.stdout.txt`.

### Synchronization ownership

This port exposes call protocols, not mbarrier channel protocols. Its 48
interpreter endpoints match six op endpoints per slot, so P-INIT has no mbarrier
endpoints to check. The semantic owner for every `init_semaphores` call is
`controller`, whose physical warp is `mk_config::NUM_WARPS - 1` (19 here).
`controller_main_loop` calls the initializer from lane 0. Internal VM prologue
barriers are different: the `threadIdx.x` predicates in `run_role_with_prologue`
initialize them in consumer warp 0. Neither internal protocol is declared as
a channel-level mbarrier protocol. `gmem_barrier_protocol` remains advisory and does
not claim stronger ordering than the upstream volatile-poll/atomicAdd protocol.
